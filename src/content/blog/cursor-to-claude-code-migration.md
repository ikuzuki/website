A year ago I would have told you that Cursor was the right answer for our team's AI-coding setup. Editor integration was the load-bearing affordance, the @-mention loop was how the work got done, and any tool that took you out of your editor was paying a tax on every keystroke. I had numbers to back it up; I'd surveyed five other engineers, watched the way they worked, and the people who used Cursor heavily were genuinely faster than the ones who hadn't adopted it. I'd been arguing internally for more aggressive Cursor adoption, not less.

We migrated off Cursor and onto Claude Code about three months ago. The thing that changed isn't Cursor (which is still a fine product) and isn't Claude Code (which has its own rough edges). What changed is what I think the load-bearing affordance is.

The story behind that is the part I want to write down.

The friction first showed up in a code review. One of the engineers on the team had written what looked like good code; the function signatures were tidy, the docstrings were there, the tests passed. But there was a small inconsistency with how the rest of the codebase named things, and a slightly different choice of typing convention than two other recent PRs had used. I asked, gently, if she'd checked the coding standards doc. She had; she'd also asked Cursor to "match the codebase style". The model had pulled from the half-dozen files she'd @-mentioned, generalised over those, and produced code that was consistent with the files it could see but inconsistent with the broader convention. The information wasn't missing; it was in the standards doc. It just hadn't been in the context.

That should have been an obvious diagnostic, but I missed the shape for another two months. I added the standards doc to a `.cursorrules` file. The next engineer to start working in a new repo copied it. Then the next. Within a couple of months three repos had drifted versions of the same standards file, two of them out of date in subtle ways, and a fresh repo someone had spun up didn't have one at all. The standards weren't enforced; they were copy-pasted, and copy-pasted things drift.

The model wasn't the problem. The model could read whatever you put in its context window. The problem was that "what's in the context window" was a per-engineer, per-session decision, made under the time pressure of "I want to write this PR". I'd been treating "what should the model know" as something a single engineer answers ad hoc in their editor. At team scale that is the wrong abstraction. The question is what the team's accumulated knowledge is, and how to put it in front of the model on every session, without the engineer having to remember.

Around then I started reading about Claude Code's plugin system more seriously. The thing that caught me wasn't the larger context window (helpful, but not load-bearing). It was the layering: per-repo `CLAUDE.md` for things true of one codebase, a team plugin for things true across all our codebases, a hook system that fires on session events. Standards live in the plugin, instances live in the per-repo file, the rule that decides which layer something belongs in is "does this apply to one repo, or to many".

I wrote a draft of what our plugin would look like, against the standards we already had. Most of `.cursorrules` belonged in the plugin; almost nothing belonged in a per-repo file. The exercise of sorting the existing content into layers turned up about a third of it that was already wrong (out-of-date Python version references, ticket-convention rules that contradicted each other, AWS region defaults from before our last cloud migration). I'd been carrying drift in plain sight for months.

Migrating the team took roughly three weeks of part-time work for me and one other engineer, then another month for the team to settle into. The work was small (most engineers just had a `.cursorrules` and a few muscle-memory habits to unlearn). The interesting stuff was structural.

The first thing I didn't expect was how much of our standards lived in skills now rather than in documents. A skill, in Claude Code's plugin model, is a markdown file with a strong description (when to fire it) and a body (what to do). Skills auto-load when the user's intent matches the description, which means a `code-review` skill fires every time someone asks for a code review, and that skill imports the coding-standards reference. The user doesn't have to remember to point at the standard; the standard finds the conversation. The first version of this was clumsy (I'd written the skill descriptions too narrowly and they weren't firing reliably), but once I'd rewritten the descriptions properly the standards started enforcing themselves. Drift stopped. PR review feedback got more consistent. Engineers stopped asking "what's our convention for X" because the convention was always present in the conversation by the time the question would have come up.

The deeper rule, which I'd guessed at but not seen demonstrated, is that hooks and skills enforce standards, prompts don't. If a rule has to be remembered to be applied, it gets forgotten. If it's hooked into the entry point (a `SessionStart` hook that nudges the developer to scaffold `CLAUDE.md` when one is missing, a pre-commit hook that auto-formats, a skill that fires on code-review intent), it's enforced. Every time I find myself writing "remember to do X" in a doc, I'm admitting the standard isn't enforced. The fix is to move it into a hook, or a skill, or accept that it'll be skipped half the time.

The second thing I didn't expect was that code review got better when I split one reviewer into many.

A single "review this PR" prompt produces reasonable output, but it's a generalist. Asking one model to simultaneously check for breaking API changes, scope creep against the ticket, test coverage gaps, silent failures, type-design weakness, comment accuracy, regression of previously-fixed bugs, and Confluence-cited standards violations means each check gets a small slice of the model's attention. Findings come back vague, miss the specific thing the team standard actually requires, and the developer learns to ignore them.

Splitting that into a handful of agents, each with its own prompt and its own narrow lens, produces sharper findings. The breaking-change detector knows what API surface looks like and ignores everything else. The silent-failure hunter knows what broad exception handling looks like and flags it specifically. They all run in parallel; the orchestrating skill collates the output. The cost is parallel sub-agents in the context budget. The benefit is findings that cite the specific team standard, with the specific line number, that the developer can act on without arguing<sup>1</sup>.

That last part is the adoption lever. Developers stop arguing with the reviewer when it points at their own team's documented standard. Without the citation, every finding is contestable. With the citation, the conversation moves on. We'd been trying to get this kind of consistency through code-review checklists for two years, with the diminishing returns you'd expect. The plugin shape got us most of the way there in a quarter.

What broke, briefly. Three things, in rough order of how much time they cost.

The first was choosing between `gh` and the GitHub MCP for repo operations. The MCP looked principled (typed tool calls, no shell-out). In practice every developer had `gh` on their machine already, authenticated, with the right org context cached. The MCP required separate auth, kept its own credential state, and broke whenever the OS keychain rotated. We moved everything to `gh` shell calls. Less typed, but actually works. The lesson, which I think generalises: prefer the thing already on the developer's machine over the thing that's architecturally cleaner.

The second was release-please. Wrong PR title prefix silently miscategorises (`feat:` versus `feature:` matters, and so does the breaking-change footer). The plugin's `coding-standards` skill now spells out the conventional-commits format and the release-please rules in one place; a commit hook validates the format before push. Before that, every release cycle had a quiet "why didn't this version bump?" conversation.

The third was migrating muscle memory, which I'm including because it's the one I'd warn the next team about. Engineers who'd built habits around Cursor's @-mention loop kept reaching for it in Claude Code and missing it. The honest answer was patience. The new model is better at team scale and worse-feeling for a few weeks because the affordance you're used to is gone. After three or four weeks people stopped noticing.

If I were starting this again with what I know now, I'd ship the plugin scaffold before the per-repo migrations. We did them in the wrong order, migrating repos first and building the plugin in parallel, which meant the first month had no team-wide standards loaded. Engineers were on whichever `CLAUDE.md` they'd hand-written and consistency was briefly worse than under Cursor. If the plugin had been the first artefact, the migration would have been a strict improvement from day one. I'd also be more aggressive about deleting `CLAUDE.md` content. Our first per-repo files were 200 lines, mostly content that belonged in skills. The rule "only what the plugin cannot know" came late.

A year ago I'd have said AI coding at team scale was about which model was best, or which editor integration was smoothest. What it actually comes down to, looking back, is whether the structure around the model is something the team controls, layered, and enforced. The model is the cheapest thing in the system. The structure is where the work is.

---

<sup>1</sup> The exact split we ended up on was eight agents: breaking-change-detector, code-reviewer (the generalist), code-simplifier, comment-analyzer, git-history-reviewer, scope-checker (matches the PR against the linked ticket), pr-test-analyzer, silent-failure-hunter. There were two we tried and dropped (a type-design analyser that was firing too often on legitimate patterns, and a comment-accuracy checker that overlapped with code-reviewer too much). The right number isn't fixed; what matters is that each agent has a narrow enough lens that its findings are specific.
